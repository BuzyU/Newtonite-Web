# Failure Modes & Resilience Matrix

Newtonite is designed so that failures degrade gracefully, preserve transactional guarantees, and provide actionable feedback rather than silent corruption or hung connections.

| Failure Mode | System Behaviour | User Effect | Proving Test |
| :--- | :--- | :--- | :--- |
| **Database Down** | Pool fails health check (`/api/v1/ready` returns 503). Pool connection timeout fires in 5000ms. | User receives 503 Service Unavailable; client UI shows retry action with clean error envelope. | `tests/concurrency.test.ts` (connection error handling) |
| **Worker Crash Mid-Job** | Row was marked `status='processing'` with `lease_expires_at = NOW() + INTERVAL '60s'`. Upon lease expiration, another worker reclaims row via `WHERE (status='pending' OR (status='processing' AND lease_expires_at < NOW()))`. | Zero lost jobs. Job processing resumes automatically without admin intervention. | `tests/outbox.test.ts` (test case: *reclaims expired worker leases after crash*) |
| **Outbox Handler Throws** | Worker catches error, logs exception, increments `attempts`, and sets `next_attempt_at` with exponential backoff (`Math.min(1000 * 2^attempts, 60000)`). After 5 attempts, transitions to `dead_letter`. | Event is quarantined; admin can view error stack trace in Dead Letters UI and click "Retry". | `tests/outbox.test.ts` (test case: *transitions to dead_letter after max attempts*) |
| **Duplicate Delivery (Worker Redelivery)** | Handler checks and records `dedupe_key` (`notification_dedupe_key` or `sla_dedupe_key`) in database unique index before dispatching. | User receives exactly one notification or email; duplicate deliveries are no-ops. | `tests/outbox.test.ts` (test case: *deduplicates notification generation on redelivery*) |
| **Delayed Worker** | Outbox rows accumulate in PostgreSQL table `outbox_events` safely within transactions. When worker wakes or scales up, it drains the queue ordered by `created_at ASC`. | Core item mutations succeed immediately (HTTP 200). Background emails/notifications deliver once worker catches up. | `tests/outbox.test.ts` (queue durability test) |
| **SSE Connection Drop** | Dedicated LISTEN client detects TCP disconnect, triggers reconnection with exponential backoff. On reconnection, broadcasts event `resync`. Client falls back to 15-second polling if SSE drops twice. | Top bar shows "Reconnecting" or "Polling" indicator. TanStack Query cache automatically invalidates on reconnect or poll. | `web/tests/setup.ts` & manual disconnect verification |
| **Client Retry After Network Timeout** | Frontend attaches unique `Idempotency-Key`. If previous execution succeeded, server returns cached HTTP response and body from `idempotency_keys` table. | Zero duplicate items or duplicate state transitions created. Replay returns original entity. | `tests/idempotency.test.ts` (test case: *replays identical response for completed key*) |
| **Stale Edit (Concurrent Mutation)** | API verifies `If-Match: "<version>"`. If record was updated by a colleague, DB version is higher than request version; server rejects with HTTP 412 `STALE_VERSION`. | UI displays "Changed while you were editing" conflict panel with server values and "Re-apply" button. | `tests/versioning.test.ts` & `web/tests/stale-edit.test.tsx` |
| **Two Claims Race** | Atomic SQL update: `UPDATE items SET assignee_id=$1 WHERE id=$2 AND assignee_id IS NULL RETURNING *`. Winner gets row; loser updates 0 rows and receives 409 `ALREADY_CLAIMED`. | Winner sees "Assigned to You". Loser receives clean notification: "Already claimed by [Name]" without UI crash. | `tests/concurrency.test.ts` (50 concurrent claims test) & `web/tests/optimistic-rollback.test.tsx` |
| **Lost Response After Successful Write** | Client times out waiting for response, but server wrote changes and stored response in `idempotency_keys`. Client retries with same `Idempotency-Key`. | Server immediately returns original stored response without re-executing business logic. | `tests/idempotency.test.ts` (test case: *duplicate key with same payload returns cached response*) |
| **Render Free Tier Cold Start** | Free instance spins down after 15 min idle. First request takes ~45 seconds while container spins up. | API client starts 3-second timer. If request takes >3s, top banner displays: *"The server is waking up, this can take up to a minute..."*. | `web/src/api.ts` (`isServerWaking` timer and wake-up banner) |
| **Supabase Project Paused (Inactivity)** | Supabase free tier pauses projects after 7 days of inactivity. | GitHub Actions keepalive workflow (`keepalive.yml`) pings `/api/v1/ready` every 10 minutes to maintain active status. | `.github/workflows/keepalive.yml` & `server/src/app.ts` (`/ready` query) |
